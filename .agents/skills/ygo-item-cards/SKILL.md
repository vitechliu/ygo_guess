# YgoGuess 道具卡

在仓库根目录工作。先读当前 `AGENTS.md`、`docs/item-cards.md`、`docs/item-card-catalog.md` 和相关代码；现有实现、用户本次要求优先于本 skill 中可能过时的细节。保留工作区已有的其他改动。

## 明确卡牌设计

从用户描述整理：道具卡名称、来源游戏王卡、抽取权重、发动时机、目标范围、效果、持续时间、重复使用规则、结束时清理规则、系统消息的可见范围。能从既有规则或上下文判断的直接实施；会改变游戏结果或泄露隐私的歧义，集中提问。用户可以在会话中设计新卡，无须先编辑表格。

玩家看到的 `description` 用简明的游戏内文案，不写“纯视觉效果”、CSS、服务端等实现术语，也不显示来源卡；`reference` 仅供设计和资料追踪。尊重用户给定的原句、署名及权重。

## 实现位置与不变量

- `shared/types.ts` 定义稳定的 `ItemCardId`、卡牌种类、房间状态和协议类型；`shared/item-cards.ts` 定义名称、来源、卡图路径、玩家文案、时机与权重。权重为 0 的卡不能被随机抽到；目前测试卡保持权重 0。
- `server/engine.ts` 的 `drawItemCard` 按正权重抽取；`activate` 在每小局玩家第 3、6、9……次实际轮到自己时发卡。第 1、2 次不发；被跳过且未开始的回合不计。新卡不得意外改变这项全局规则。`useItemCard` 校验本人回合、卡牌实例和合法目标，消费后由服务端执行效果。需要随机数时也在服务端产生。
- `Entry.itemCards` 是持久化的私有手牌，`RoomView.myItemCards` 只给持有者。看透卡一类信息只通过定向系统消息告知使用者；公共聊天仅公告可公开的信息。不得把自己的未知题目或其他人的手牌意外下发给客户端。道具卡产生的系统消息使用 `kind: 'item-card'`，沿用与普通消息不同的样式。
- 目标选择、按钮状态与客户端展示在 `client/ItemHand.tsx`；房间/协议处理在 `server/hub.ts`。视觉效果由服务端记录必要的目标和到期时间，客户端在 `client/` 中用 CSS/组件呈现；到期及本小局结算时清除。纯口头约定的卡只需准确公告，不额外制作输入、限制或计数机制。
- 保持一次性使用、本人回合发动、房主可关闭道具卡的现有通用规则，除非用户明确修改。调试控制台可定向发卡以复现效果，但不得成为正式服务的入口。

## 卡图

默认优先找来源游戏王卡的原版卡图，裁切**插画区域**，不把卡名、外框和效果文字缩进插画；用户特别允许天变卡使用自制图。确实需要原创贴图或用户要求重绘时才生成新图。道具卡插画保存到 `public/`，尽量压成约 300×300 WebP；蟑螂等独立特效贴图要更小。压缩后实际查看成品，确认主体可辨、裁切无误，并在需要时记录来源链接。卡框颜色由 `category` 沿用来源种类（魔法绿、陷阱紫红、普通怪兽棕、超量黑、同调白）。

## 同步与验证

更新 `docs/item-card-catalog.md` 的名称、来源、状态、功能、备注，必要时更新 `docs/item-cards.md` 和 `README.md` 的规则说明。`已上线` 只表示已实际部署且玩家可用，代码完成不能据此标为已上线。检查 UI 中是否仍有旧规则文案。

为规则、权重边界、目标校验、隐私、持续时间和结算清理添加聚焦测试；视觉修改需要实际查看成品，必要时跑对应浏览器流程并留截图。可用 `npm run dev` 的房主道具卡调试控制台定向发卡。按 `AGENTS.md` 使用 Node.js 24，运行 `npm test` 和 `npm run build`；影响回合、协议或游戏核心行为时按 `README.md` 同步推进 `package.json` 与 `package-lock.json` 版本号。若测试受运行环境影响，分别报告已通过的检查与未验证部分，不把原生运行时崩溃称作规则测试失败。
